# 可复用执行经验

本文件是所有 App、Sheet 和模块的通用执行规则。应用专属的 resource-id、坐标和页面名称只能补充规则，不能绕过下面的门禁。

## 1. 页面身份必须使用页面契约

页面契约至少包含：

- 目标页面的稳定身份特征：顶部标题、页面专属 resource-id、页面专属控件或明确的页面标签；
- 当前行操作前的页面谓词；
- 只负责公共导航的进入函数；
- 导航后重新读取页面状态的复核步骤。

通用容器、底部 Tab 选中状态、任意行情控件或上一行留下的页面状态都不能单独证明已进入目标页。若多个页面共享相同文字，优先使用“标题 + 专属页面标识”的组合。例如国投港股首页使用“顶部标题栏=港股 + `ganggu_page`”；其他 App 也应寻找同等强度的专属身份组合。

每行固定执行：

```text
状态复位 → 判断目标页
  ├─ 是：执行本行操作
  └─ 否：公共导航 → 重新校验目标页
                 ├─ 成功：执行本行操作
                 └─ 失败：阻塞，禁止执行本行操作
```

公共导航不能被写入本行 `actual`，也不能把导航成功当作业务动作成功。

## 1.1 页面分组必须携带完整导航上下文

“个股详情页”不是足够的分组条件。至少使用 `sheet + 一级目录 + 二级目录 + 三级目录 + 四级目录 + 入口` 生成页面组键；例如“沪深A股→个股详情”和“港股→个股详情”必须是两个组。Excel 合并单元格产生的空层级要向下继承，但遇到新的上级目录时必须清除旧的子级目录。

页面组只允许复用入口导航和已验证的定位策略，不允许合并业务动作。组内每行仍要独立执行、独立截图、独立断言和立即落盘；页面被上一行改变时，先恢复组锚点。页面组按连续 Excel 行形成，不能为了分组而打乱 `source_order`。

Plan 是 LLM 的首轮执行建议，但执行器只消费计划中已校验的动作。首轮目标页校验失败时最多执行一次计划内的 `recovery_navigation` 并重新检查目标页；仍失败就阻塞本行。阻塞复测若启用 `--llm-retest`，则由独立 retester 会话重新读取原始用例和实时证据，旧 Plan 仅供审计。

## 2. 入口查找必须有限且双向

进入目标子页面前按固定顺序查找入口：

1. 查找当前可见区域；
2. 没找到时回到页面顶部，再查找一次；
3. 顶部仍没找到时向下查找底部区域，最后再查找一次；
4. 仍未找到则阻塞，不继续猜坐标、无限滑动或重复点击。

每次点击入口后都要重新读取页面并校验目标子页面。页面发生跳转后，不得继续把原首页入口点击发送到子页面。

同一 Excel 行如果描述多个入口，必须把它们当作多个独立子动作：

```text
恢复来源页 → 找入口 → 点击 → 校验目标子页
恢复来源页 → 找下一个入口 → 点击 → 校验目标子页
```

来源页恢复失败、入口缺失或目标子页复核失败，立即结束该行并记录阻塞原因。

## 2.1 列表、横屏和排序的通用规划技巧

以下规则适用于所有 App；它们是观察和规划规则，不是固定坐标。规划时只在当前用例适用时加入，并根据当前 UI 树或截图动态确定控件、列表容器和滑动范围：

- **横屏列表页标题**：列表切换横屏后可能不显示页面标题。横屏目标页不能把标题作为唯一门禁条件，应组合方向状态、页面专属 resource-id/控件、表头、列表容器和可见数据确认目标页；如果标题属于预期展示内容，将标题缺失单独记录，不能直接判定横屏失败。
- **列表滑动生效**：滑动前 observe 并记录列表第一行股票名称和股票代码；滑动一次后再次 observe。比较前后第一行名称/代码组合，组合变化才判定滑动生效，不能只依据 swipe 返回成功；无法读出前后数据时标记待验证。
- **目标元素未找到**：已确认进入目标页但未找到元素时，先在当前区域查找，再回到最顶部并查找；顶部仍没有时最多下划三个屏幕，每次下划后查找一次。第 3 屏后仍没有就阻塞/待验证，不得无限滑动或盲点坐标。
- **列表排序校验**：点击指定字段表头前，observe 并记录列表前两条数据及字段值；点击后再次 observe。只有前两条数据发生变化且指定字段顺序与点击前相反，才判定排序生效；只看到点击成功、数据未变化或字段无法读取时不得判定通过。

## 3. 冷启动和重试边界

- 模块首次进入、App 崩溃/卡死或有限返回无法恢复时才冷启动；普通行之间复用进程并软复位。
- 同一动作最多自动重试 1 次；每次尝试都必须进入 `action_trace`。
- 不允许用“再点几次”“继续返回”“无限重启”掩盖页面契约失败。
- 行级 journal 必须在本行结束后立即落盘，暂停时只补跑未完成行。

## 4. 结果质量门

正式报告前必须通过完整性门和结果质量门：

- `actual` 必须同时包含两部分：基于真实 `action_trace` 的可读执行步骤，以及与证据截图对应的可见文字/标题/页面结果；禁止抄写 Excel `action`、公共导航或“截图已保存”等回显句；
- 原始 UI 树只能放在 `page_observation` 等证据字段，不能单独充当 `actual`；若截图无法确认结果，明确写“无法仅凭页面文本确认”，不得由 LLM 猜测；
- 每条记录必须有 `sheet`、Excel `row`、状态、真实 `action_trace`、观察结果和独立 evidence；
- 观察类用例只能标为待验证，不能因为截图存在就自动通过；
- 同一页面的观察文字可以在不同用例中合法重复，但必须同时有该行自己的 action/expected 上下文和独立 evidence；没有上下文的跨用例重复 actual 继续判为疑似通用结果；
- evidence 路径必须与当前用例绑定，不能复用上一行截图；
- 质量门失败时停止生成正式报告，先修正记录或执行器，不能通过降低门槛强行回填。

## 5. 异常处理口径

模块完成后只把失败、阻塞、待验证和低置信度记录交给 LLM 集中分析。LLM 可以解释证据和给出复测建议，但不能覆盖确定性页面/动作门禁，也不能把未执行写成通过。

首轮结束后默认把阻塞用例集中到延迟复测队列，逐条重新 setup 并复测一次；兼容模式重放已校验 Plan，`--llm-retest` 模式由独立会话重新理解并逐步执行。仍阻塞就保留最终状态，不自动无限复测。其他未通过状态可在 LLM 复核后按需显式加入通用复测队列。

## 6. 画像反哺口径

每轮执行生成 `profile_feedback.json`，候选必须包含导航上下文、页面观察、执行行号、截图证据、App 版本和运行目录。LLM 只能基于这些事实审核候选；单次观察或单次异常不得直接覆盖正式画像。升级画像前必须通过 `reback_run` 的 schema 校验、去重和 `lint_profile`，Markdown 只能由 `derive_docs.py` 派生。
