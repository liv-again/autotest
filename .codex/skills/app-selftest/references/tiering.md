# tiering — 分档口径（客户端自测，已与用户确认）

## 默认只测 high

跑 Excel 用例做自测时，**默认只按「优先级」列过滤出 `high`**；`low`/`middle` 除非用户明确说"全测"，否则跳过（[[feedback-high-priority-only]]）。开跑前先按 `优先级` 列过滤，用 `battleplan.py`/枚举脚本时加 `优先级==high` 过滤；不确定范围就先问一句"这次只测 high 还是全测？"，别默认全量。

- 同屏顺手能验的 low/middle 可以捎带记 incidental（一屏多用例成本低），但**不为 low/middle 专门导航/造数据/建链**，且 incidental **不计入承诺覆盖**。
- 冻结 `selection` 时把范围写进 `selection.yaml`，用户确认后生成 `scope_hash`——之后跑批以此为准，范围可审计、不临场扩大。

## 分档判据（两个降级判据，仅此两个）

只用两个降级判据：
1. 需**测试数据**（某状态标的/权限/持仓/历史）
2. 需**交易时段/盘中**

命中任一 → 🟡；否则 → 🟢（⬜=iOS，不适用平台）。

**"与自营/PC/两端对比一致""走势图视觉正确"这类预期不作降级项**——在客户端自测场景，一致性/视觉正确性判断不是我方职责，我方只要**驱动到位 + 保证有数据 + 有截图**就算通过；两端是否真的一致，是**测试团队**后续核对的事（[[feedback-selftest-green-definition]]）。

- 全表分布参考（753行样本）：🟢33% / 🟡64% / ⬜；仅 high（389行）：🟢39% / 🟡60%。
- 分档属于测前筛选与 skill 流程；`tools/annotate_excel.py` 只回填执行器传入的 `tier`，未提供时沿用源表的“优先级”，不会根据用例文案临场推断。

## 目标代码缺失 → ❌错误（禁止替代）

用例指定的**目标代码**（标的/证券代码）在 App 内搜索无结果时：

- **直接判 ❌错误（⛔）**，不得改用其他市场/其他标的代码代替。
- 不得标 🟡需数据、不得标 🟢通过，更不得"换一个代码把步骤跑完"。
- 代码缺失 = 用例前提不成立，如实记录"目标代码 XXX 在当前 App/环境不可用"，交测试/产品确认（可能是不支持该品种、代码错误或环境未备数据）。

> 反例（已发生过，务必避免）：2026-08-19 中邮证券批次，搜索 950002 无结果后改用 510050（上证50ETF）验证——这是错误行为，会让结果张冠李戴、误导结论。目标代码搜不到就是搜不到，如实报 ❌。

## BLOCKED_ENVIRONMENT（环境降级导致的阻塞，独立列示）

自动降级到 `confirm_only` 后（`env.yaml` 未认证/过期/撤销/包或版本或账户不匹配），**依赖真实提交/撤单的用例不得因为驱动到确认框就判通过**——一律标 `BLOCKED_ENVIRONMENT`：

- **不计入通过率**（既不算通过、也不算失败）。
- 报告显式提示"因环境未认证/降级而阻塞"，与 ✅通过 / 🟡待数据 / ☑不适用分开列示，不得与 ✅ 混算。
- 权威定义见 `safety-policy.md` §5.1；本文件只声明分档口径里如何呈现该状态。
